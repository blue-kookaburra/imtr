# City Loop Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Model the City Loop so Flagstaff, Melbourne Central and Parliament draw on the SVG map with real per-line disruption status, unblocking the `svg-network-map` merge.

**Architecture:** The loop is an *overlay entity* beside `LINES` — a ring of stations plus per-group ordering, from which `build.ts` derives extra stations and extra edges. The 16 line arrays in `lib/network/data.ts` are never touched, because `scripts/extract_map.py`, the geometry build, the spans logic and the scraper's station matching all key off them. Section matching (which stations a disruption covers) switches from reading `line.stations` directly to reading a derived *match sequence* that splices the loop in ahead of the trunk.

**Tech Stack:** TypeScript, Next.js 16 (App Router, Turbopack), Vitest, Node scripts for geometry generation.

## Global Constraints

- **Fail-visible principle.** Anything the parser cannot confidently map to track segments renders as a line-level ⚠ warning — never a possibly-wrong blackout, never a false "all clear". Loop work must preserve this exactly.
- **`LINES` arrays in `lib/network/data.ts` are immutable in this plan.** No loop station may be added to any of the 16 `stations: [...]` arrays. Adding one silently re-keys edge ids, breaks `scripts/extract_map.py`'s parsing of that file, and invalidates `data/map-geometry.json`.
- **`data/map-geometry.json` is generated — never hand-edit it.** Fix geometry in `data/map-overrides.json`, then rerun `npm run map:build`.
- **`npm run lint` has 3 pre-existing errors** (`CalendarScreen.tsx:58`, `MapScreen.tsx:~68`, `StationSearch.tsx:33`, all `react-hooks/set-state-in-effect`). These predate this work. The bar is *no new errors*, not a clean run.
- **Baseline service:** a loop station is served whenever a line serving it runs. No loop-specific timetable windows.
- **Timezone:** everything user-facing is Australia/Melbourne (`lib/meltz.ts`, `lib/spans.ts`). Never use raw `toISOString().slice(0,10)` for a user-facing date.
- **Tests run against real fixtures** in `tests/fixtures/` — extend fixtures rather than mocking.
- Baseline before this plan: **47 tests passing**, `npx tsc --noEmit` clean, `npm run build` succeeds.

**Ground truth** (verified by colour-sampling `docs/network-map.png` against the group colours; the ring carries exactly four lanes — yellow, red, navy, green — for nine lines):

| Group | Colour | Lines | Outbound order from Flinders Street | Portal |
|---|---|---|---|---|
| Northern | `YELLOW` | craigieburn, upfield | parliament → melbourne-central → flagstaff | north-melbourne |
| Clifton Hill | `RED` | mernda, hurstbridge | southern-cross → flagstaff → melbourne-central → parliament | jolimont |
| Burnley | `NAVY` | belgrave, lilydale, alamein, glen-waverley | southern-cross → flagstaff → melbourne-central → parliament | richmond |
| Caulfield | `GREEN` | frankston | southern-cross → flagstaff → melbourne-central → parliament | richmond |

Northern runs the ring in the opposite direction to the other three — that is the real Melbourne arrangement and it is why `order` is per-group rather than a single global ring order.

Note `southern-cross` appears in the Northern lines' trunk arrays already but is **not** in the Northern `order`; the Northern loop path leaves Flinders Street towards Parliament. Conversely `southern-cross` is in the Burnley/Clifton Hill/Caulfield `order` but not in those lines' trunks.

**Design note:** loop edges are *added to*, not substituted for, the existing trunk edges. `belgrave:flinders-street-richmond` (the direct path) must survive alongside the new loop chain, because both are drawn on the poster and both carry trains.

The per-line loop chain for a group is: `flinders-street` → each station in `order` → `portal`. For Burnley that is `flinders-street → southern-cross → flagstaff → melbourne-central → parliament → richmond`, giving five edges per line.

Loop stations get `x: 0, y: 0` — the schematic coords are legacy (superseded by `data/map-geometry.json`, which has real poster coordinates for all three) and nothing renders from them.

In `lib/network/build.ts`, add after the `LINE_BY_ID` export (currently line 72):

```ts
// The order used to decide which stations a disruption's section covers.
// Distinct from both the drawn geometry and the LINES arrays: a loop-served
// line's section can run through the ring, so the ring is spliced in ahead of
// the trunk. Non-loop lines are just their trunk.
const MATCH_SEQUENCES = new Map<LineId, string[]>(
  LINES.map((line) => {
    const group = LOOP.groups.find((g) => g.lines.includes(line.id));
    if (!group) return [line.id, line.stations];
    return [line.id, [line.stations[0], ...group.order, ...line.stations.slice(1)]];
  })
);

export function matchSequence(lineId: LineId): string[] {
  return MATCH_SEQUENCES.get(lineId) ?? [];
}
```

Then rewire `edgesBetween` to use it — replace its body's three uses of `line.stations`:

```ts
export function edgesBetween(lineId: LineId, a: string, b: string): Edge[] {
  const seq = matchSequence(lineId);
  const ia = seq.indexOf(a);
  const ib = seq.indexOf(b);
  if (ia === -1 || ib === -1) return [];
  const [lo, hi] = ia < ib ? [ia, ib] : [ib, ia];
  return EDGES.filter((e) => {
    if (e.lineId !== lineId) return false;
    const i = seq.indexOf(e.from);
    return i >= lo && i < hi;
  });
}
```

The `LINE_BY_ID` lookup and its early return are no longer needed — `matchSequence` returns `[]` for an unknown line, and `indexOf` on `[]` is `-1`, so the guard still holds.

`lineSpan`:

```ts
function lineSpan(d: Disruption, lineId: LineId): { from: string; to: string } | null {
  if (!d.parsed) return null;
  const mentioned = d.stations ?? (d.fromStation && d.toStation ? [d.fromStation, d.toStation] : []);
  const seq = matchSequence(lineId);
  if (seq.length === 0) return null;
  const idxs = mentioned
    .map((s) => seq.indexOf(s))
    .filter((i) => i !== -1)
    .sort((a, b) => a - b);
  if (idxs.length < 2) return null;
  return { from: seq[idxs[0]], to: seq[idxs[idxs.length - 1]] };
}
```

`stationInSection`:

```ts
function stationInSection(stationId: string, d: Disruption, lineId: LineId): boolean {
  if (d.wholeLine || !d.parsed) return true;
  const span = lineSpan(d, lineId);
  if (!span) return false;
  const seq = matchSequence(lineId);
  const i = seq.indexOf(stationId);
  const lo = seq.indexOf(span.from);
  const hi = seq.indexOf(span.to);
  return i !== -1 && i >= lo && i <= hi;
}
```

`reachableFromBeyond`:

```ts
function reachableFromBeyond(
  stationId: string,
  span: { from: string; to: string },
  lineId: LineId
): boolean {
  const seq = matchSequence(lineId);
  const i = seq.indexOf(stationId);
  if (i === -1) return false;
  if (stationId === span.from) return i > 0;
  if (stationId === span.to) return i < seq.length - 1;
  return false;
}

### Task 6: Loop-only disruptions

The pattern the old model could not express: the line runs, the ring does not.

> **AMENDED 2026-08-04, after the Task 6 review.** The design below — represent a loop
> closure as a station *span* anchored at Flinders Street — is **wrong and must not be
> implemented as written**. An adversarial review executed the committed code and found
> four Critical defects, all caused by this design rather than by the implementer:
>
> 1. `lineSpan` spans min..max *index*, and `reachableFromBeyond` requires `i > 0` for a
>    span's start to count as `boundary`. `flinders-street` is always index 0, so it is
>    reported **`cut` on every loop-only disruption on every affected line** — while the
>    disruption text says trains run *to* Flinders Street.
> 2. The same index span sweeps in `southern-cross` on the three groups whose ring order
>    contains it, undoing this task's deliberate exclusion of it.
> 3. `not stop at flagstaff` alone claimed the whole ring was shut, even for text that
>    says the other loop stations are fine.
> 4. `"Buses run direct to Flinders Street"` — realistic whole-line bus-replacement
>    phrasing — was read as a loop-only section, setting `wholeLine: false` so every
>    trunk station reported `normal`. A **false all-clear**, the worst fail-visible
>    failure mode this project has.
>
> **Root cause:** a loop closure is not a contiguous section between two stations. It is
> "these three specific stations are skipped, and nothing else changes". A span cannot
> express that, so the span representation is replaced.
>
> **Ruling (user, 2026-08-04):** keep full fidelity — model it properly rather than
> dropping the feature or merely narrowing the regex.
>
> **Replacement design:**
> - `Disruption` gains `skipsStations?: string[]` — "exactly these stations are skipped;
>   the line otherwise runs". It is deliberately NOT a span and never widens.
> - The parser sets `skipsStations: ["flagstaff", "melbourne-central", "parliament"]`
>   and leaves `stations`/`fromStation`/`toStation` unset for a loop closure.
>   `flinders-street` and `southern-cross` are on the surface route every train uses and
>   are never skipped.
> - `lib/status.ts` handles `skipsStations` directly: those stations are `cut` on the
>   affected lines; the ring edges between them are severed; **no other station or edge
>   is touched**. That last clause is the whole point and needs a test.
> - `LOOP_CLOSED` narrows: the subject must be *trains* (not buses), and a single loop
>   station being named is not a ring closure. It also gains "City Loop closed" and
>   "not run through the City Loop", which it previously missed.
> - Tests must exercise `computeStationStatuses`, not only `sectionStations`. Every one
>   of the four defects above was invisible to tests that stopped at the parser.

export function sectionStations(text: string): string[] | null {
  const m = text.match(
    /(?:between|from)\s+([A-Za-z',\/ ]+?)(?:\.|,?\s+(?:each|nightly|daily|after|until|while|due|stations|when|what|why)\b|\s+\d|$)/i
  );
  if (m) {
    const parts = m[1].split(/,|\/|\band\b|\bto\b/i);
    const ids = [...new Set(parts.map(resolveStation).filter((s): s is string => !!s))];
    if (ids.length >= 2) return ids;
  }
  // No explicit section, but the text says the ring is shut.
  if (LOOP_CLOSED.test(text)) return [...LOOP_SECTION];
  return null;
}
```

Note the restructure: the explicit branch now falls *through* to the loop check when it finds fewer than two stations, instead of returning `null` immediately.

```python
"""One-shot helper: trace the City Loop ring lanes off the poster raster.

Prints an `edges` fragment to paste into data/map-overrides.json. Each colour
group gets its own lane, offset perpendicular to the ring centreline, matching
how the poster draws four parallel loops.

Run: python scripts/trace_loop_ring.py
"""
import json
import math

STATIONS = json.load(open("data/map-stations.json"))["stations"]

# Ring anchors in drawn order around the loop.
RING = ["flinders-street", "southern-cross", "flagstaff", "melbourne-central", "parliament"]

# Perpendicular offset per group, in poster pixels, measured off the artwork:
# the four lanes sit inside one another. Negative is towards the ring centre.
LANE = {"YELLOW": -18.0, "RED": -6.0, "NAVY": 6.0, "GREEN": 18.0}


def offset_segment(a, b, d):
    """Shift the segment a->b sideways by d pixels."""
    dx, dy = b[0] - a[0], b[1] - a[1]
    n = math.hypot(dx, dy) or 1.0
    px, py = -dy / n * d, dx / n * d
    return [a[0] + px, a[1] + py], [b[0] + px, b[1] + py]


def main():
    out = {}
    for group, d in LANE.items():
        for i in range(len(RING)):
            a_id, b_id = RING[i], RING[(i + 1) % len(RING)]
            a, b = STATIONS[a_id], STATIONS[b_id]
            pa, pb = offset_segment(a, b, d)
            out[f"{group}:{a_id}-{b_id}"] = [
                [round(a[0], 1), round(a[1], 1)],
                [round(pa[0], 1), round(pa[1], 1)],
                [round(pb[0], 1), round(pb[1], 1)],
                [round(b[0], 1), round(b[1], 1)],
            ]
    print(json.dumps(out, indent=2))


if __name__ == "__main__":
    main()
```

**Deliberate deviations from the spec:**

- The spec described ring-segment edges plus "one portal edge per group". Because lines within a group share the ring but each line needs its own edge id (the convention `${lineId}:${from}-${to}` is load-bearing for `data/map-geometry.json` and for `SegmentStatus.edgeId`), edges are per *line*, with lines in a group sharing coordinates. Four visible lanes, nine lines' worth of ids.
- The spec left per-group ring connectivity to implementation-time tracing. Task 1 fixes it as data with a stated ground truth, because every later task needs it to be decided. Northern running the ring opposite to the other three groups is the substantive finding.
- The spec said a loop station's `lines` is "the union of its serving groups' lines". Southern Cross therefore gains navy, red and green — it is on those groups' ring order though absent from their trunk arrays. Task 2 tests this explicitly since it is surprising.

**Known limitation, accepted:** with a section running through the ring, the parallel *direct* edge for that same line (e.g. `belgrave:flinders-street-richmond` during a Parliament–Box Hill closure) keeps its own status rather than inheriting the section's. Both readings are defensible and the current one under-warns on a segment other lines still serve normally. Task 3's `edgesBetween` test pins the behaviour so a future change is deliberate.
